# 학습 로드맵

6일 일정은 학습 속도에 따라 조정한다. 단계마다 개발자가 구현하고 검토와 검증을 거친다.

| 날짜 | 학습과 직접 구현 | 확인할 결과 |
| --- | --- | --- |
| 10/22 | 초기 구조 확인, JDK/네트워크 정리, Initializr/Wrapper 준비, 순수 Java 판정 연습 | Gradle 기본 테스트 및 S/B 단위 테스트 |
| 10/23 | 클래스/생성자/enum/컬렉션, 상태와 게임 규칙 | 입력 검증과 게임 상태 전이 이해 |
| 10/24 | Docker Compose PostgreSQL, Entity/Repository/JPA | 저장/조회, SQL, 연관관계와 변경 감지 확인 |
| 10/25 | Controller/Service/DTO, 게임 시작/조회/추측 | 요청부터 DB까지 흐름과 비밀 숫자 비노출 확인 |
| 10/26 | Security 인증/소유권, 보상 트랜잭션 | 다른 플레이어 접근 차단, 중복/동시 보상 테스트 |
| 10/27 | 통합 테스트와 문서 정리, 여유가 있으면 간단한 프론트 | 전체 흐름 직접 설명 및 재현 |

보상 단계에서는 게임별 RewardHistory의 UNIQUE 제약과 잠금 전략을 검토한다.
같은 게임의 중복 지급뿐 아니라 같은 플레이어의 여러 게임 보상에 따른 잔액 갱신도 검증한다.
API 경로와 DTO는 구현 단계에서 확정한다. 초기에는 Security/Compose/React를 추가하지 않는다.

## 첫 번째 Java 실습 (아직 구현하지 않음)

1. `com.example.quest504.game` 아래 Spring 의존성이 없는 `GuessResult`와 `NumberBaseballJudge`를 직접 설계한다.
2. `judge("123", "132")`의 반환값은 1S 2B이다. 생성자는 객체의 초기 상태를 정하고, 반환 객체는 두 판정값을 묶는다.
3. JUnit에서 정답 3S 0B, 전부 불일치 0S 0B, 자리만 다른 경우 0S 3B를 확인한다.
4. 길이 3, 숫자 1~9, 중복 금지 검증을 어느 클래스가 맡을지 설명하고 잘못된 입력 테스트를 추가한다.
5. 고정 정답으로 판정을 먼저 이해한 뒤 무작위 생성, 저장, HTTP 연결로 확장한다.

목표는 정답 문자열과 입력 문자열을 받아 결과 객체를 반환하는 데이터 흐름을 직접 설명하는 것이다.
